# Відповідність завданням

## Заняття 5: Головне меню і навігація

NavHost і NavController з’єднують огляд та журнал. Пункти меню доступні в прокручуваному рядку; вихід повертає користувача до форми входу. Детальний екран detail/{id} отримує ідентифікатор через аргумент NavController; тест перевіряє, що відкривається потрібний пост.

Реалізація: `ui/Screens.kt: MonitorApp`.

## Заняття 6: Форма введення та перевірка

Форма поста містить назву, тип, потужність дози, потужність станції та координати. Порожні назви, нескінченні числа й координати поза діапазоном відхиляються до запису в базу. Під email і паролем додано підказки, а дубль email відхиляє mock API з HTTP 400.

Реалізація: `MeasurementForm; MonitorLogic.validate`.

## Заняття 7: Архітектура MVVM

ViewModel містить стан екрана й запускає корутини у viewModelScope. Compose отримує StateFlow через collectAsStateWithLifecycle. UI не виконує SQL-запитів. Код фізично поділено на пакети ui, viewmodel, domain, data та device.

Реалізація: `viewmodel/MonitorViewModel.kt`.

## Заняття 8: База даних Room

Сутність Measurement має первинний ключ id. DAO реалізує вставку/оновлення, спостереження Flow і видалення. Записи зберігаються після перезапуску процесу, тоді як демонстраційний сеанс входу створюється заново. Додано другу таблицю ChangeEvent зі зв’язком один-до-багатьох, зовнішнім ключем, індексом і каскадним видаленням. @Transaction атомарно зберігає пост та подію; @Upsert не стирає історію. SQL обчислює COUNT, AVG і MAX. Міграція 1→2 зберігає наявні записи.

Реалізація: `data/Data.kt: MeasurementDao, MonitorDatabase`.
